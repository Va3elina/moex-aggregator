# Как мы работаем в этом репозитории

Короткий свод правил для совместной работы над Frame (таймфрейм.рф).
Нас двое, репозиторий один — этих правил достаточно, чтобы не мешать друг другу
и не ронять прод.

---

## Главное в трёх строчках

1. **`origin/main` — единственный источник правды И прод одновременно.**
   Пуш/мёрж в `main` запускает CI, который **сам деплоит на таймфрейм.рф**.
2. Поэтому **в `main` напрямую не коммитим.** Любая задача = **своя ветка → Pull
   Request → мёрж**.
3. Перед началом работы — всегда `git pull --rebase`. Коммитим мелко и часто.

> ⚠️ **GitHub НЕ блокирует push в `main` технически** — это договорённость, а не
> защита: `main` без branch protection, любой `git push origin main` пройдёт и
> молча задеплоится на прод. Ответственность на нас. Хотим жёстко — включаем
> защиту ветки (см. [«Сделать правило железным»](#сделать-правило-железным-опционально) внизу).

---

## Почему именно так (один важный факт про наш CI)

- `build.yml` запускается **и на push в `main`, и на каждый Pull Request** →
  **PR автоматически прогоняет сборку** (видно зелёный/красный билд).
- `deploy.yml` запускается **только после успешной сборки на `main`**.

Отсюда железное правило репозитория:

> **PR проверяется сборкой, но НЕ деплоится. Деплоит только мёрж в `main`.**

То есть ветка+PR — это бесплатный предохранитель: сломанный код ловится в PR
**до** того, как уедет на прод. А ещё это снимает гонку деплоев: 14.06.2026
два деплоя от пачки прямых пушей в `main` столкнулись на пересоздании
контейнера (`removal of container ... is already in progress`) и один упал.
Когда правки копятся в ветке и уезжают одним мёржем — таких накладок нет.

## Дневной цикл (копипаст)

```bash
# 1. Старт ЛЮБОЙ задачи — всегда от свежего main
git checkout main
git pull --rebase origin main
git checkout -b fix/oi-period-selector       # ветка под задачу

# 2. Работаешь, коммитишь мелко и часто
git add <конкретные файлы>                    # не `git add -A` вслепую
git commit -m "fix(oi): ..."

# 3. Пушишь ВЕТКУ — это НЕ деплой, прод не трогается
git push -u origin fix/oi-period-selector

# 4. Открываешь Pull Request и СРАЗУ ставишь авто-мёрж
gh pr create --base main --fill
gh pr merge --auto --squash --delete-branch   # смёржится САМ по зелёному билду
gh pr view --web                              # (опц.) открыть PR в браузере (диф, ревью)

# Всё. Как только build-check позеленеет — GitHub мёржит, мёрж запускает деплой.
# Ждать и жать руками ничего не нужно. Если хочешь следить:
gh pr checks --watch                          # живой статус build-check
```

## Именование веток

`fix/` · `feat/` · `style/` · `refactor/` · `chore/` · `docs/` + короткий kebab.
Примеры: `fix/oi-period-selector`, `feat/news-ingest`, `chore/team-workflow`.

---

## Коммиты

Формат — Conventional Commits, тема по-русски:

```
type(scope): краткая тема (50–72 символа)

Тело: объясняет ПОЧЕМУ, а не ЧТО. 2–4 предложения. Side-effects, причины,
рассмотренные альтернативы.
```

- **Типы:** `fix` · `feat` · `refactor` · `chore` · `docs` · `style` (только
  визуал/CSS, без логики) · `revert` (автоген от `git revert`).
- **Scope:** индикатор (`oi`, `buffett`, `funds`, `heatmap`, `seasonality`…) или
  область (`api`, `frontend`, `deploy`, `data`).
- Не сваливай несвязанные изменения в один коммит — разделяй по смыслу.
- AI-ассистент добавляет в свои коммиты `Co-Authored-By:` со своей моделью.
  Футер «Generated with…» не добавляем.

## Pull Request

- Открывай через `gh pr create --base main --fill` (или в вебе).
- CI сам прогонит `build-check` на PR (это ЕДИНСТВЕННЫЙ прогон сборки — на main
  после мёржа билд НЕ повторяется, деплой стартует сразу; ускорено 2026-07-02).
- **Ревью лёгкое.** Нас двое и мы доверяем друг другу:
  - мелочь (фронт-полиш, доки) — **авто-мёрж**: сразу после создания PR
    `gh pr merge --auto --squash --delete-branch` — смёржится сам по зелёному;
  - рисковое (`api/`, `signals/`, биллинг, миграции БД) — авто-мёрж НЕ ставь,
    пусть второй глянет, потом мёрж руками.
- Мёрж — `--squash --delete-branch`, чтобы история была чистой, а ветки не копились.
- **Мёрж в `main` = деплой.** Мёржи, когда готов выкатывать.

### Когда можно прямой push в `main` (исключение)

Прямой `git push origin main` в обход PR — только для **уже завершённой,
проверенной мелочи**, когда заводить PR — избыточная церемония (опечатка в доке,
hotfix в одну строку, перенос уже готовой работы). Всё остальное — через PR.
Если сомневаешься — делай PR.

## Если что-то пошло не так

- **Случайно закоммитил в `main` (ещё не запушил):** перенеси работу в ветку и
  верни `main` на место —
  `git branch fix/моя-работа && git reset --hard origin/main`.
- **Уже запушил в `main` по ошибке:** скорее всего, это **уже запустило деплой** —
  проверь `gh run list --branch main`. Откатывай через **`git revert <sha>` + PR**,
  а НЕ force-push (force в `main` запрещён).
- **Ветка отстала от `main`:** `git fetch origin && git rebase origin/main` →
  разреши конфликты (`git add <файл>` → `git rebase --continue`) →
  `git push --force-with-lease` (ветка переписана, обычный push отклонится).
- **PR показывает конфликты** («This branch has conflicts»): то же самое — на
  своей ветке `git fetch && git rebase origin/main`, разреши, `git push
  --force-with-lease`; PR пере-проверится и станет мёржабельным. `gh pr merge`
  с конфликтами не смёржит.

## Синхронизация и конфликты

- `git pull --rebase` перед стартом задачи и перед мёржем — чтобы не дрейфовать
  на десятки коммитов позади.
- Конфликт при rebase → резолвишь, `git add <файл>`, `git rebase --continue`.
  **Без merge-коммитов** — у нас линейная история.
- **Никогда `git push --force` в `main`.** В свою ветку можно, но только
  `--force-with-lease`.

---

## Прод и деплой

- **Деплоит CI, не руки.** Мёрж/push в `main` → `deploy-prod` СРАЗУ (заходит на
  сервер по SSH сам; гейт сборки уже отработал на PR, повторного билда на main
  нет — с 2026-07-02). Руками по SSH **не деплоим**.
- **Сервер `/opt/frame` — чистый deploy-target, НЕ воркспейс.** Деплой делает
  `git reset --hard origin/main` → **любая ручная правка или `scp` прямо на проде
  СТИРАЕТСЯ** следующим деплоем. Все изменения — только через git.
- SSH на прод остаётся нужен только для логов, SQL/БД, инспекции и аварийного
  деплоя (если CI недоступен).
- Здоровье прода: `curl https://таймфрейм.рф/health` → `{"status":"ok",...}`
  (через nginx эквивалентен `/api/health`).

## Что НЕ коммитим

`.env` и любые секреты/ключи/токены · `.dev-pids/` · `/tmp/*` ·
WIP-эксперименты, которые попросили пока не коммитить.
`/data/` и `signals/data/` игнорируются (якорь от корня — чтобы не задеть
`frontend/src/data`, где туры/методология). Полный список always-exclude
паттернов — в скилле `moex-git-workflow`.

---

## Двое в репо — одно простое правило

Договоритесь в чате/телеге, **кто какой кусок трогает сегодня**. Когда вас
двое, одной строчки достаточно, чтобы не редактировать один и тот же файл
одновременно — это убирает 90% конфликтов ещё до их появления.

---

## Сделать правило железным (опционально)

Сейчас «не коммить в `main`» — на честном слове. Чтобы GitHub **технически**
требовал PR и зелёный build-check перед попаданием в `main`, включается branch
protection (Settings → Branches, или `gh api`): require pull request + require
status check `build-check`. После этого прямой push в `main` будет отклоняться —
весь остальной этот документ станет самоисполняющимся. Решаем вдвоём, нужно ли.
