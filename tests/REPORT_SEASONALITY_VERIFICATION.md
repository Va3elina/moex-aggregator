## Этап 1: Дивидендная коррекция (режим "Цена") {#этап-1}

### 1.1. Что делалось

Режим "Цена" показывает два графика: **сырая цена закрытия** (close) и **скорректированная цена** (adjusted close) — цена без дивидендных гэпов. Adjusted close нужна чтобы визуально оценить реальную динамику акции, исключив искусственные просадки в дни выплаты дивидендов.

Задача: убедиться что формула adjusted close даёт корректный результат.

### 1.2. Формула adjusted close

**Метод:** мультипликативная коррекция (стандарт Yahoo Finance / CRSP).

**Идея:** на каждую экс-дивидендную дату (день, когда акция торгуется "без дивиденда") вычисляется корректирующий множитель. Все цены ДО этой даты умножаются на этот множитель, что "убирает" гэп.

**Формула:**

```
множитель = (цена_закрытия_накануне − сумма_дивиденда) / цена_закрытия_накануне
```

Где:
- **цена_закрытия_накануне** — close последнего торгового дня ПЕРЕД экс-датой (сырая, нескорректированная)
- **сумма_дивиденда** — размер дивидендной выплаты на одну акцию (руб.)
- **множитель** — число от 0 до 1, показывающее долю цены, оставшуюся после вычета дивиденда

**Пример для SBER (экс-дата 2024-07-11, дивиденд 33.30₽):**
```
цена_закрытия_накануне = 316.68₽
множитель = (316.68 − 33.30) / 316.68 = 0.8948
```
Все цены до 2024-07-11 умножаются на 0.8948. Это снижает их на ~10.5%, что соответствует дивидендной доходности.

**Порядок обработки:** дивиденды обрабатываются от старых к новым. Каждый множитель применяется ко всем ценам до соответствующей экс-даты. Итоговая скорректированная цена = сырая цена × произведение всех применимых множителей.

### 1.3. Найденный и исправленный баг

**Проблема:** в исходной реализации формула использовала уже скорректированную цену на экс-дате (`adjusted[ex_idx]`) вместо сырой цены накануне (`closes[ex_idx - 1]`).

**Почему это было ошибкой:** при обработке нескольких дивидендов каждый последующий множитель вычислялся на основе цены, уже уменьшенной предыдущими коррекциями. Это делало множитель слишком агрессивным и занижало прошлые цены.

**Масштаб ошибки:**
- Кумулятивный adjusted return ДО исправления: **+1316%**
- Кумулятивный adjusted return ПОСЛЕ исправления: **+540%**
- Правильный total return (ручной пересчёт с реинвестированием): **+528%**
- Ошибка до исправления: **125%** расхождение
- Ошибка после исправления: **1.95%** расхождение (приемлемо для мультипликативного метода)

**Исправление:** заменено `adjusted[ex_idx]` на `closes[ex_idx - 1]` (строка формулы в `api/routers/seasonality.py`).

### 1.4. Проверка данных дивидендов

**Источники данных:** ISS MOEX (основной, ежедневное обновление) + dohod.ru (историческая загрузка).

**Таблица `dividends`:** содержит поля `secid` (тикер), `registry_close_date` (дата закрытия реестра), `ex_date` (экс-дивидендная дата), `value` (сумма дивиденда).

**Экс-дата определяется эмпирически:** алгоритм ищет день, в который гэп открытия (цена_закрытия_накануне − цена_открытия) примерно равен сумме дивиденда, в окне ±5 дней от даты закрытия реестра.

**Результаты проверки качества (с 2015 года):**

| Метрика | Значение |
|---------|----------|
| Всего экс-дат | 1007 |
| Совпадают с реальным гэпом (40-200%) | 883 (87.7%) |
| Не совпадают | 124 (12.3%) |

**Причины несовпадений:**
- Мелкие дивиденды (< 1₽), где гэп тонет в рыночном шуме
- Неверно определённые экс-даты (цена выросла вместо падения)
- Влияние на итоговый результат минимально (множитель ≈ 0.999)

### 1.5. Чистка до-сплитовых артефактов

**Проблема:** ISS MOEX для акций, прошедших сплит (дробление), возвращает дивиденды и в до-сплитовом, и в пост-сплитовом выражении.

**Пример GMKN (сплит 1:100):**
```
2018-07-13: дивиденд 607.98₽ (до-сплитовый) ← УДАЛЁН
2018-07-16: дивиденд 6.08₽ (пост-сплитовый) ← ОСТАВЛЕН
```

**Критерий удаления:** `сумма_дивиденда > цена_закрытия_на_экс-дате` (дивиденд не может быть больше цены акции).

**Удалено:** 27 записей (GMKN: 21, TRNFP: 6).

## Этап 2: Сезонность (режим "Гистограмма") {#этап-2}

### 2.1. Что делалось

Режим "Сезонность" показывает средний дневной return (изменение цены) по группам: часы дня (intraday), дни недели (weekday), дни месяца (monthday), месяцы года (monthly).

Задача: убедиться что формула расчёта returns корректна, и что дивидендная коррекция в режиме `exclude_dividends=True` работает правильно.

### 2.2. Формула расчёта returns

**Без дивидендной коррекции (`exclude_dividends=False`):**

```
дневной_return = (цена_закрытия_сегодня − цена_закрытия_вчера) / цена_закрытия_вчера × 100%
```

Где:
- **цена_закрытия_сегодня** — close текущего торгового дня
- **цена_закрытия_вчера** — close предыдущего торгового дня (не календарного, а торгового — пропускаются выходные и праздники)

**С дивидендной коррекцией (`exclude_dividends=True`):**

Сначала строится массив скорректированных цен (adjusted close) по той же мультипликативной формуле что в Этапе 1. Затем returns считаются по скорректированным ценам:

```
adj_return = (adj_close_сегодня − adj_close_вчера) / adj_close_вчера × 100%
```

Это убирает искажение от дивидендных гэпов: на экс-дате вместо резкого падения (из-за вычета дивиденда из цены) будет показана реальная динамика без этого эффекта.

**Ранее использовалась аддитивная формула:**
```
скорр_return = (close + дивиденд − prev_close) / prev_close × 100%
```
Она заменена на мультипликативную для консистентности с режимом "Цена".

### 2.3. Режимы группировки

| Режим | Ключ группировки | Итерация (единица периода) | Пример: 90 итераций |
|-------|-----------------|---------------------------|---------------------|
| intraday | Час дня (10-18) | Торговый день | 90 последних торговых дней |
| weekday | День недели (Пн-Пт) | Неделя | 90 последних недель |
| monthday | День месяца (1-31) | Месяц | 90 последних месяцев (~7.5 лет) |
| monthly | Месяц (Янв-Дек) | Год | 90 последних лет (или сколько есть данных) |

**Фильтрация выходных:** для режимов weekday, monthday, monthly применяется фильтр `ISODOW BETWEEN 1 AND 5` (только Пн-Пт). Это исключает артефактные свечи на выходных, которые иногда появляются в данных Algopack.

## Критический анализ: верны ли сами способы проверки? {#критика}

### Что мы проверяли и чего не проверяли

#### Уровень 1: Математическая корректность (проверено)

**Вопрос:** правильно ли код реализует заявленные формулы?

**Метод:** `verify_seasonality.py` — независимая Python-реализация тех же формул, сравнение с API.

**Ограничение:** это проверка "код делает то, что задумано". Но если формула сама по себе неверна — обе реализации дадут одинаково неверный результат. Тест покажет 0.0000% расхождение, но обе стороны будут ошибаться одинаково.

**Вывод:** этот уровень закрыт полностью. Если где-то в коде ошибка (off-by-one, неверный фильтр, неправильный JOIN) — скрипт её найдёт, потому что пишет запросы к базе напрямую, минуя API.

#### Уровень 2: Правильность формулы (проверено частично)

**Вопрос:** верна ли сама формула? Считаем ли мы то, что нужно?

**Метод для adjusted close:** сравнение кумулятивного adjusted return с ручным total return (реинвестирование дивидендов). Расхождение 1.95%.

**Что это доказывает:** мультипликативная формула корректно приближает полный доход с учётом дивидендов. 1.95% расхождение — это свойство метода (Yahoo/CRSP), а не ошибка. Метод является отраслевым стандартом, используется Yahoo Finance, Bloomberg, CRSP.

**Метод для сезонности:** сравнение с TradingView PineScript на тех же данных (MOEX:SBER). Расхождение 0.01-0.03%.

**Что это доказывает:** наша формула close-to-close return идентична тому, как считает TV. Расхождение обусловлено разными источниками данных (TV feed vs Algopack), а не формулой.

**Чего не доказывает:** что close-to-close return — это единственно правильный способ считать сезонность. Можно было бы считать open-to-open, или log-returns, или взвешенные по объёму returns. Мы выбрали close-to-close как наиболее распространённый и совместимый с другими платформами.

#### Уровень 3: Правильность данных (проверено частично)

**Вопрос:** верны ли исходные данные (свечи, дивиденды)?

**Свечи:** приходят из Algopack (официальный API MOEX). Перекрёстная проверка — сравнение с TradingView. Цены close совпадают с точностью до ±0.5% (разные поставщики данных для одной биржи).

**Дивиденды — суммы:** загружены из ISS MOEX (официальный источник) и dohod.ru (агрегатор). Перекрёстной проверки сумм с третьим источником не проводилось. Суммы принимаются как данность от MOEX.

**Дивиденды — экс-даты:** определяются эмпирически (поиск гэпа). 87.7% совпадают с реальным гэпом. Для остальных 12.3% экс-дата может быть сдвинута на 1-2 дня. Влияние на adjusted close минимально (множитель тот же, применяется к ±1 свече).

**Непроверенный риск:** если MOEX или dohod.ru содержат ошибку в сумме дивиденда — мы её воспроизведём. Для крупных тикеров (SBER, LKOH, GAZP) это маловероятно, для мелких — возможно.

#### Уровень 4: Смысловая адекватность (проверено через референс)

**Вопрос:** показывает ли инструмент то, что имеет смысл с точки зрения рынка?

**Метод:** сравнение с наблюдениями из рабочей торговой стратегии "Трендовушка-Универсалка".

**Что подтвердилось:**
- Intraday паттерн (рост утром/вечером) — да, наш инструмент это показывает
- Sell in May (зима >> лето) — да, на IMOEX разница 19x
- Эти паттерны широко известны и документированы в академической литературе

**Что не подтвердилось:**
- Weekday (Пн/Вт рост, Ср/Чт падение) — за текущие 90 недель не подтвердилось для SBER. Автор стратегии сам отмечал нестабильность этого паттерна.
- Monthday (начало месяца лучше) — не подтвердилось для SBER за 30 месяцев.

**Что это значит:** несовпадение отдельных наблюдений не говорит об ошибке инструмента. Сезонные паттерны нестабильны по определению — они могут усиливаться, ослабевать и инвертироваться с течением времени. Инструмент правильно показывает текущее состояние, даже если оно не совпадает с историческим наблюдением.

### Слабые стороны процесса верификации

1. **Нет эталонного внешнего источника для adjusted close РФ акций.** Yahoo не корректирует MOEX, TV тоже. Bloomberg и Reuters недоступны. Мы проверяли формулу математически (vs manual reinvestment), но не vs внешний провайдер.

2. **Верификация сезонности замкнута на один тикер (SBER).** Все тесты проводились для SBER. Другие тикеры (LKOH, GAZP, MTSS) не тестировались отдельно. Предположение: если формула верна для SBER — она верна для всех, т.к. код общий.

3. **PineScript проверка — однократная и ручная.** Скрипт нужно вставить в TV вручную, результаты сверять глазами. Нет автоматизированного CI-теста. При изменении кода нужно перезапускать вручную.

4. **Intraday режим не имеет внешней числовой проверки.** Мы подтвердили паттерн качественно ("рост утром/вечером"), но не сравнивали конкретные числа с TV или другим источником. Причина: TV PineScript для intraday MOEX на часовых свечах требует отдельного скрипта, который не был написан.

5. **Дивидендная коррекция для сезонности невозможно проверить извне.** TV не корректирует дивиденды для РФ. Мы доказали внутреннюю согласованность (96/96), но не сравнили с внешним "правильным ответом". Единственная гарантия — что формула стандартная (Yahoo/CRSP) и математически корректная.

### Что можно улучшить в будущем

1. **Добавить второй тикер в автотесты** (например LKOH) — убедиться что код работает не только для SBER.
2. **Написать PineScript для intraday** — числовое сравнение часовых returns с TV.
3. **Автоматический CI-тест** — скрипт, запускаемый при деплое, который проверяет что API returns не "уплыли" относительно зафиксированного baseline.
4. **Мониторинг качества экс-дат** — при загрузке новых дивидендов автоматически проверять совпадение с гэпом.
5. **Сравнение с Barchart.com** для SPY — скачать adjusted close через yfinance, прогнать нашу формулу, сравнить с публичными данными. Это верифицирует формулу на международных данных, где внешний эталон доступен.
